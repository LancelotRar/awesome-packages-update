# Spec: 恢复自动化门禁并重构检测/投递管线

Status: ready-for-agent

## Problem Statement

维护者在 `main` 上删掉了 workflow 里唯一的 lint + 单测步骤（`a7563dd`），同时把单测搬到了根目录 `tests/`。结果有三层问题：

1. **质量门禁消失**：137 个测试没有任何自动化执行路径，`tests/` 只是摆设；AGENTS.md 里"提交前必跑 ruff 与 pytest"变成纯荣誉制度。测试文件还各自带一份 `sys.path.insert` 样板，加一个新测试要先抄这段路径魔法。
2. **入口结构在恶化**：`run_checks` 的主流程是一条 147 行的函数，五个分支（检测失败、无 release、无变化、资产未命中、投递失败/成功）各自重复"记日志 → 改状态 → 追加列表 → 写摘要行"，还配了三套并行账本（按 id 的结果字典、失败列表、投递列表），"未变化数"由减法推出；同一条惰性打开 Telegram 客户端的逻辑被逐字复制两次。漏掉结果的启用条目会被摘要静默标成"已关闭"。
3. **共享语义被重复实现**：扫描结果用 `error`、`problem`、`detection is None` 三个字段交叉编码四种状态，两个入口（每日检查与每周资产审计）各自重写同一套四路级联，措辞与日志级别已经漂移；`scan` 专门暴露的 `problem` 字段只有一个调用方在用。检测阶段还会对同一批资产过滤两次，`asset_count` 在 `latest` 与 `tag` 两种策略下含义不同（全部资产 vs 命中资产），日志与审计各自按不同理解使用它。

## Solution

把这次"搬测试、删门禁"的改动补完，并顺手把管线收敛到单一模型：

- 新增独立 CI workflow，在 push / pull_request 上跑钉死版本的 ruff + pytest；发布 workflow 保持单一职责（检测、投递、提交状态），不再兼职跑测试。
- 用 pytest 的 `pythonpath` 配置替代 11 份 `sys.path.insert`，本地与 CI 使用同一条命令。
- 检测/投递管线只保留一个"每项结果"模型：扫描产出显式状态与唯一原因，投递产出显式结果；摘要、计数、退出码、状态落盘全部从结果派生。
- 每个条目的状态在它结算后立即落盘，崩溃、取消、超时都不会导致已发消息重发。
- Telegram 连接配置与消息文案配置分开，环境变量只在一个工厂里读取；配置错误统一抛出、在入口处捕获一次。

对外行为保持不变：通知文案、marker 格式、`state.json` 结构、日志事件名、摘要行文本与顺序、退出码语义、检测策略语义全部与改造前一致。

## User Stories

1. 作为维护者，我希望每次 push / PR 都自动跑 ruff 与 pytest，这样回归会在合并前被拦住，而不是靠提交前自觉。
2. 作为维护者，我希望 CI 里的 ruff / pytest 版本是钉死的，这样新版本规则变化不会让门禁莫名其妙变红或变绿。
3. 作为维护者，我希望发布 workflow 只做"检测 → 投递 → 提交状态"，这样测试结果不会与状态提交交织在一起，失败语义也不会互相污染。
4. 作为维护者，我希望本地命令与 CI 完全一致（同样的 lint 范围、同样的测试入口），这样"本地绿了"就等于"CI 绿了"。
5. 作为维护者，我希望新增测试不用再抄 `sys.path` 样板，这样加测试的成本只剩测试本身。
6. 作为维护者，我希望 lint 同时覆盖 `scripts` 与 `tests`，这样测试代码不会成为规则盲区。
7. 作为频道订阅者，我希望改造后收到的通知文案与现在逐字一致，这样不会出现突然的格式变化。
8. 作为频道订阅者，我希望 `latest` / `tag` 两种检测策略、预发布跳过、tag 通配过滤的语义都不变，这样既不漏版本也不重复推送。
9. 作为频道订阅者，我希望真实更新仍然至少投递一次，这样一次失败的运行不会静默吞掉一个版本。
10. 作为维护者，我希望 marker 的格式不变（`tag@指纹` 与纯指纹两种），这样部署这次改造不会触发全量重发。
11. 作为维护者，我希望 `state.json` 的结构不变，这样现有状态文件无需迁移即可继续使用。
12. 作为维护者，我希望日志事件名与字段名不变（`update_detected`、`unchanged`、`assets_unmatched`、`run_finished` 等），这样已保存的日志查询与 Actions 注解标题继续有效。
13. 作为维护者，我希望运行摘要的行文本（`✅ delivered`、`➖ unchanged`、`❌ detection` 等）与行顺序不变，这样不同日期的运行页面可以直接对比。
14. 作为维护者，我希望退出码语义不变（任一条目失败即非 0），这样外层自动化不需要改判断。
15. 作为值班者，我希望每个条目一结算就把状态写盘，这样任务超时或被取消后，下次运行不会把已经投递过的版本再发一遍。
16. 作为值班者，我希望中途异常终止时留下的状态文件仍然是完整合法的 JSON，这样下一次运行能正常从断点继续。
17. 作为值班者，我希望连续失败告警仍然在状态安全落盘之后才发送，这样告警本身出问题也不会丢掉 marker。
18. 作为值班者，我希望告警标记（`alerted`）也能持久化，这样同一个条目不会每次运行都重复告警。
19. 作为 AFK agent，我希望每个条目的处理结果是一个显式对象（结果类型 + 详情），这样新增一种失败模式只是加一个枚举值，而不是在五处复制分支。
20. 作为 AFK agent，我希望摘要、计数、退出码全部从结果列表派生，这样它们不可能互相矛盾。
21. 作为 AFK agent，我希望"没有结果"不会被渲染成"已关闭"，这样程序缺陷不会被摘要掩盖。
22. 作为 AFK agent，我希望惰性打开 Telegram 客户端的逻辑只有一份，这样连接失败、复用、快速失败的行为只在一个地方定义。
23. 作为 AFK agent，我希望扫描结果暴露显式状态（就绪 / 无 release / 检测失败 / 资产未命中），这样调用方不需要靠字段组合猜语义，也不可能构造出自相矛盾的结果。
24. 作为 AFK agent，我希望"资产未命中"与"检测失败"各自只有一个规范原因字符串，由 `scan` 统一构造，这样每日检查与每周审计不会再说出不同的话。
25. 作为 AFK agent，我希望 `Detection` 直接携带命中资产，这样过滤只发生一次，`scan` 不需要重复跑一遍过滤器。
26. 作为 AFK agent，我希望资产计数只有一个含义（命中数），这样日志里的 `assets=` 与审计的"有没有资产"判断不会再各说各话。
27. 作为 AFK agent，我希望 Telegram 的凭据配置与消息文案配置分开，这样增删一个文案字段不必碰连接配置，也不必逐字段搬运。
28. 作为 AFK agent，我希望消息构造只接收一个文案对象，而不是六个散装字符串，这样参数表不会继续膨胀。
29. 作为 AFK agent，我希望两个入口共用同一个 Telegram 配置工厂，这样它们不可能用不同方式解释环境变量。
30. 作为 AFK agent，我希望配置缺失以异常形式抛出，并在入口处统一捕获、记一条 `config_error`、返回 1，这样缺 secret 不会在投递或告警中途硬退出。
31. 作为 AFK agent，我希望纯文本通知路径复用已有的 `send_text`，这样"逐 chat 发送 + FloodWait + 部分失败"只有一份实现。
32. 作为审计运营者，我希望每周审计使用的状态与原因与每日检查完全一致，这样同一个故障在两个入口读起来是同一句话。
33. 作为审计运营者，我希望审计策略不变（声明了 include 但零命中即失败；无 include 的零资产只是警告），这样不会误报或漏报。
34. 作为维护者，我希望测试断言的是外部行为（状态、退出码、摘要、发送内容、状态文件），这样后续重构不需要重写测试。
35. 作为维护者，我希望 README 与 AGENTS.md 里的测试命令、测试位置、样板说明与实际一致，这样贡献者不会把已删除的路径魔法重新加回来。

## Implementation Decisions

### 门禁与测试导入

- 新增独立 CI workflow：`push` 与 `pull_request` 触发，安装钉死版本的 ruff / pytest（沿用被删步骤里的版本），依次执行 `ruff check scripts tests` 与 `pytest tests -q`。发布 workflow 删除测试步骤的现状保留，不再加回。
- 新增项目级 pytest 配置，用 `pythonpath = ["scripts"]` 让 `tests/` 下的模块可直接 `import state`、`import scan` 等；删除所有测试文件里的 `sys.path.insert` 样板。
- `ruff.toml` 的规则集保持不变（仍是有意收窄的基线），只扩大被检查的目录范围。
- AGENTS.md 中"每个测试文件自带 `sys.path.insert`，没有 conftest"的约定随之更新为"导入路径由 pytest 配置提供"；README 的本地运行章节保持与 CI 同一组命令。

### 扫描层（`scan` / `detector`）

- `Detection` 成为唯一携带资产的模型：release、marker、命中资产元组。删除 `asset_count`；所有需要计数的地方使用 `len(detection.matched)`，日志字段 `assets=` 的含义固定为"命中资产数"。
- `detect` 在构造 marker 的同时把命中资产放进 `Detection`；`scan_item` 不再二次调用资产过滤。
- `ScanResult` 用显式状态替代字段组合：`READY` / `NO_RELEASES` / `DETECTION_FAILED` / `ASSETS_UNMATCHED`，外加唯一的 `reason` 字符串（仅后两种状态有值）。构造时校验状态与字段的一致性，使"健康但没有检测结果"这类组合不可表示。
- 原因字符串只由 `scan` 构造：检测失败与资产未命中各一句，包含仓库、tag、过滤串等上下文。每日检查与每周审计都只消费 `reason`，不再各自拼接。
- `tag` 策略在零命中时仍然在检测阶段失败（保持现有语义），只是原因文本统一由扫描层生成。

### 投递管线（`run_checks`）

- 引入每项结果模型，结果类型即摘要表格中显示的结果文本，保证摘要字符串零变化。形状如下（来自本轮审查中的原型草图，仅保留决策相关部分）：

  ```python
  class OutcomeKind(StrEnum):
      DELIVERED = "✅ delivered"
      UNCHANGED = "➖ unchanged"
      NO_RELEASES = "➖ no releases"
      DISABLED = "⏭ disabled"
      NO_ASSETS = "❌ no assets"
      DETECTION_FAILED = "❌ detection"
      DELIVERY_FAILED = "❌ delivery"

  @dataclass(frozen=True)
  class Outcome:
      item_id: str
      kind: OutcomeKind
      detail: str = ""
  ```

- 主流程按监控项顺序产出 `Outcome` 列表；`delivered` / `failed` / `unchanged` / `skipped` 计数由结果统计得出，摘要行由结果直接渲染，不再维护按 id 的结果字典与两个并行列表，也不再用减法推算"未变化"。
- 每个条目的处理抽成一个函数（输入扫描结果、状态、会话、目标 chat、force；输出 `Outcome`）。状态在条目结算后立即保存；原先"全部结束后统一保存"的调用删除。告警阶段仍在其后执行，若产生了新的 `alerted` 标记再补一次保存。
- 惰性客户端收成一个小对象，暴露单一的"取客户端"方法，内部持有客户端与首次失败原因；投递阶段与告警阶段共用它，删除两份重复的打开逻辑与跨阶段共享的局部变量。
- 告警、摘要、退出码的对外行为不变：阈值仍是连续 3 次失败；未配置管理会话时仍然只记一条警告；任一条目失败返回 1。

### Telegram 配置（`notifier` / `env`）

- `TelegramConfig` 只保留连接与目标：bot token、chat id 列表、api id、api hash。
- 消息文案使用清单里已有的文案类型（标题、描述、群组/频道/项目链接、话题标签）直接传入通知函数；消息构造器改为接收该文案对象，而不是六个独立字符串。
- 环境变量只在 `env` 里读取一次，形成"给定 chat id 列表 → 连接配置"的工厂；每日检查与每周审计共用它。缺失或非法值抛配置错误（继承自 `RuntimeError`），入口统一转成 `config_error` 日志 + 退出码 1。
- 删除投递路径里逐字段搬运文案的辅助函数，以及审计里独立拼装连接配置的代码。
- 纯文本通知路径直接调用 `send_text`，删除复制的逐 chat 发送循环；相册路径、批量上限、caption 位置、上传一次多 chat 复用等行为不变。

### 文档与一致性

- README 的目录章节补上每周审计入口，修正"唯一入口"的表述；测试命令、测试位置与 CI 保持一致。
- 日志事件名、字段名、摘要字符串、marker 格式、`state.json` 结构均为冻结契约，本次改造不得改变。

## Testing Decisions

**合格测试的标准**：只断言外部可观察行为——退出码、`state.json` 内容、Actions 摘要文件内容、实际发送的文本/文件参数、扫描结果的状态与原因、抛出的异常类型与消息。不断言私有函数、调用顺序、内部字段组合；不为"实现看起来对"写测试。用户可见字符串（摘要行、通知文案、告警文案）一旦变化必须由测试显式失败。

**接缝（已与用户确认）**：只用现有接缝，不新增。

1. 最高接缝是两个入口：`run_checks.main()` 与 `audit_assets.main()`，通过环境变量注入配置，monkeypatch 现有协作者（清单加载、`scan_item`、`notify`、`open_client`、`send_text`），断言退出码、状态文件、摘要、发送记录。
2. 策略接缝是 `scan_item(item, token)` 与 `detector.detect`（HTTP 在 `detector.fetch_releases` / `fetch_release_by_tag` 处替换），断言状态、原因、marker、命中资产。
3. 投递接缝是 `notify(release, copy, client, assets, token)` 配一个内存假客户端，断言发送参数与返回值契约。
4. 不引入统一 HTTP 客户端接缝，也不迁移现有 monkeypatch 方式。

**受影响的测试模块**

- `test_scan.py`：改为断言状态与唯一原因；新增"检测失败的原因同时可用于两个入口"；`READY` 必须携带检测结果；删除对 `asset_count` 的构造。
- `test_detector.py`：断言 `Detection.matched` 的内容与 marker 的对应关系；删除 `asset_count` 断言；保留"元数据变更不改 marker""被过滤掉的资产不影响 marker"等既有契约。
- `test_run_checks.py`：保留现有全部行为用例（投递/未变化/失败计数/检测隔离/force/未知项目/告警/禁用/摘要顺序/客户端复用）。新增两条：条目结算即落盘（让第二个条目的投递抛出无法被捕获的中断，断言第一个条目的 marker 已在文件中）；摘要中不会出现被误标为"已关闭"的启用条目。现有 `_run` 辅助函数继续作为主夹具，返回值保持外部视角。
- `test_audit_assets.py`：保留零命中、无资产、检测失败、Telegram 报告等用例；新增"审计报告中的检测失败文本与扫描层原因一致"，确保两个入口不再漂移。
- `test_notifier.py`：保留全部文案与相册契约用例；纯文本路径改为经由 `send_text` 后，仍以"每个 chat 都收到、部分失败返回 False"等外部行为断言，不新增对内部调用的断言。
- `test_env.py`：新增配置工厂用例（完整环境成功、缺失项抛配置错误、非法 api id 抛配置错误）。
- 其余测试（`test_state.py`、`test_watchlist.py`、`test_projects_yaml.py`、`test_logs.py`、`test_timestamps.py`、`test_github_api.py`）不改断言，仅删除 `sys.path` 样板。

**先例**：`test_run_checks.py` 已经用"patch 协作者 + 断言状态文件/退出码/发送记录"的方式覆盖主流程；`test_scan.py` 与 `test_audit_assets.py` 已经用假检测结果覆盖策略分支；`test_notifier.py` 已经用内存假客户端覆盖投递契约。新增测试沿用这些写法，不引入新夹具框架。

## Out of Scope

- 状态提交策略：workflow 里 `git rebase -X theirs` 与三次重试的合并语义、是否改成每项一个状态文件。这会改变运维行为，需要单独决策。
- 上传路径的内存与并发改造：整文件读入、`BytesIO`、无界并发、流式上传、可中断超时。需要真实大资产测量后再定。
- 类型收紧与死代码清理：`StateEntry` TypedDict、marker 时间戳迁移探针、GitHub 请求头构造函数合并、不可达分支删除。
- 相册 caption 归属位置的存疑行为（当前挂在批次最后一项，未在真实频道验证）。
- 检测策略、资产过滤语法、通知文案、`projects.yaml` 清单内容、cron 时间、checkout 策略的变更。
- 为重复投递做去重收据；投递语义仍是至少一次。
- 新增监控项或调整现有条目的过滤条件。

## Further Notes

- **冻结契约**：通知文案、marker 格式、`state.json` 结构、日志事件名与字段、摘要行文本与顺序、退出码。任何一条在改造中发生变化，都视为破坏性变更，应拆成单独提案。
- **落地顺序**：先加 CI（独立、零风险，先恢复门禁），再做扫描层与投递管线的重构（三者互相咬合：结果模型依赖扫描状态，单次过滤依赖 `Detection.matched`），最后做配置拆分与文档同步。每步都应保持全绿。
- **风险**：逐项落盘会增加文件写入次数（当前清单不足 50 项，量级可忽略），但会改变"状态文件只在运行结束变化"的观察方式；若未来引入并发投递，需要重新确认落盘时序。
